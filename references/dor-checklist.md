# Definition of Ready 检查清单

检查每一项时记录证据来源。`[关键]` 项缺失时不得判定“通过”；不适用项必须说明原因，而不是直接勾选。

## 业务目标

- [ ] [关键] 业务问题和目标明确
- [ ] 目标用户和使用场景明确
- [ ] 成功指标或预期结果明确
- [ ] [关键] 范围明确
- [ ] 非目标明确

## 流程与规则

- [ ] [关键] 主流程明确
- [ ] [关键] 异常流程明确
- [ ] [关键] 状态变化明确或明确不涉及状态变化
- [ ] 关键字段明确
- [ ] 枚举明确
- [ ] 唯一性和去重规则明确
- [ ] [关键] 幂等规则明确或有不适用说明
- [ ] [关键] 并发冲突规则明确或有不适用说明

## 权限与数据

- [ ] [关键] 操作权限明确
- [ ] [关键] 数据范围明确
- [ ] [关键] 租户或机构隔离明确或确认不适用
- [ ] [关键] 敏感数据处理明确或确认不涉及敏感数据
- [ ] 历史数据影响明确

## 技术与交付

- [ ] 涉及模块已识别
- [ ] [关键] 数据库影响已识别
- [ ] [关键] API影响已识别
- [ ] 第三方依赖已识别
- [ ] [关键] 验收标准可测试
- [ ] 测试环境或测试数据可用
- [ ] 发布风险已识别
- [ ] 不存在未关闭 P0 问题

## 结论规则

- **通过**：全部 `[关键]` 项有证据，其他未完成项不影响进入开发且已登记负责人和期限。
- **有条件通过**：不存在 P0；仅剩可在编码开始前关闭的 P1，并且负责人、期限和验证方式明确。不得以“有条件通过”为由绕过核心业务规则。
- **不通过**：存在 P0，或任一 `[关键]` 项缺失且会导致实现、测试或安全边界无法确定。

## 问题分级约束

- 缺少规则或证据通常记为 P1；一般性补充项记为 P2。
- 只有已有证据表明会发生数据丢失、严重安全事件或核心业务不可用时，才记为 P0。
- 不得把“可能产生 P0 后果”的所有未知项直接升级为 P0。
